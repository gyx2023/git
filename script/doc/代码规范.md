## 1. git版本分支规范
### 分支命名规范
1. feature/xxxx/base：功能开发分支，从 dev 检出，开发完成后合并回 dev。
2. fix：修复分支，根据问题来源从不同分支检出：
   1. 开发阶段问题：从 dev 检出，修复后合并回 dev。
   2. 预生产阶段问题：从 pre 检出，修复后合并回 pre，并同步到 dev。
   3. 生产环境紧急问题：从 master 检出，修复后合并到 master，并同步到 pre 和 dev,也叫hotfix分支
3. release：上线分支，从 dev 检出，用于准备特定版本的上线。在分支上进行最后的测试、配置调整等，测试通过后合并到 master 和 pre，并打上版本标签。
4. dev：开发集成分支，所有功能开发、日常修复首先合并到此分支进行集成测试。
5. master: 主分支，对应生产环境代码，始终保持稳定、可发布状态。只接受从 release-* 分支的合并。
6. pre: 预生产分支，用于模拟生产环境进行最终验证。定期从 master 或 release-* 同步，确保与生产环境一致。
7. tag标签：v<主版本>.<次版本>.<修订版本>，如 v1.2.3
### 分支合并原则
1. 单向流动：代码变更应遵循从下游分支向上游分支逐步合并的原则，避免反向合并造成混乱。
2. 及时同步：定期从上游分支合并变更到当前分支，减少长期分支带来的冲突风险。
3. 最小化冲突：通过规范分支创建来源和合并目标，确保冲突范围可控。
4. 原子提交：每个合并操作应保持功能完整，提交信息清晰，便于追溯。
### 分支合并流程
#### 功能开发流程
创建功能分支：从最新的 dev 分支检出 feature/<功能名称>/base。
开发与自测：在功能分支上进行开发，定期从 dev 合并最新变更（git merge dev），保持与集成分支同步。
合并回 dev：开发完成并通过自测后，发起合并请求（MR/PR）将 feature 分支合并到 dev。合并前确保 dev 已包含最新代码，并解决所有冲突。
删除功能分支：合并完成后删除远程功能分支，保持仓库整洁。
#### 日常修复流程（非紧急）
开发阶段问题：同功能开发流程，从 dev 检出 fix/xxx，修复后合并回 dev。
预生产阶段问题：从 pre 检出 fix/xxx，修复并验证后合并回 pre，同时将修复同步到 dev（可 cherry-pick 或合并 fix 分支到 dev）。
#### 上线发布流程
创建 release 分支：当 dev 达到可发布状态时，从 dev 检出 release-<yyyyMMdd>（例如 release-20250315）。
预发布验证：在 release 分支上进行最终测试、配置调整、文档更新等。此阶段发现的修复直接提交到 release 分支，并同时合并回 dev（避免 dev 遗漏修复）。
合并到 master：测试通过后，将 release 分支合并到 master。合并后需在 master 上打上版本标签（如 v1.2.3）。
同步到 pre：将 release 分支合并到 pre，更新预生产环境。
清理 release 分支：合并完成后删除远程 release 分支（可选保留，但建议删除以保持简洁）。
同步 master 到 dev：将 master 合并回 dev，确保 dev 包含生产最新代码（尤其是可能存在的 hotfix）。
#### 生产紧急修复（hotfix）
创建 hotfix 分支：从 master 检出 fix/<紧急问题>（或 hotfix/xxx，按需命名）。
修复与验证：在分支上修复问题，并在本地验证。
合并到 master：将 fix 分支合并到 master，并打上新的补丁版本标签。
同步到 pre 和 dev：将 fix 分支分别合并到 pre 和 dev，确保所有环境一致。
删除 hotfix 分支：完成后删除远程分支。
### 合并顺序示意图
```mermaid

feature/xxx         fix/xxx (开发)
↓                   ↓
└────→ dev ←─────── fix/xxx (预生产/生产)
        ↓
    release-<date>
    ↓        ↓
    master   pre
    ↓        ↓
    └──────→ dev (同步)
```
### 冲突处理策略
- 定期同步：开发人员应每天至少一次从上游分支（如 dev）合并到自己的功能分支，避免长时间分歧。
- 合并前更新：在发起合并请求前，确保本地分支已合并最新的目标分支代码，并解决所有冲突。
- 冲突解决原则：
  - 代码冲突时，与相关开发人员沟通确认，确保合并结果正确。
  - 对于配置文件等易冲突文件，尽量使用模板化或环境变量减少直接修改。
  - 复杂冲突可考虑在本地进行 rebase（但需谨慎，已推送的分支避免 rebase）。
  - 使用合并请求（MR/PR）：通过代码审查工具进行合并，审查者需确认冲突已正确解决。
### 注意事项
- 禁止直接向 master、pre 提交代码，必须通过合并请求。
- 合并操作尽量使用 --no-ff 保留分支历史（除非明确需要线性历史）。
- 定期清理已合并的远程分支，保持仓库整洁。
- 合并时提交信息应清晰描述变更内容，如“Merge branch 'feature/xxx' into dev”。
